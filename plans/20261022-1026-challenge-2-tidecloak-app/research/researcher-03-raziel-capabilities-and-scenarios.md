# TideCloak capability and scenario digest

**Decision summary.** The strongest buildable trust primitive for a one-day prototype is client-side self-encryption or the built-in `RelationshipAttestation:1` per-record encrypt/decrypt policy. The latter is **not patient/owner-controlled sharing**: only a `tide-realm-admin` can grant by approving a policy in the Tide enclave. Arbitrary Forseti signing, general attestations, and portable provenance claims need a custom contract, which the pack says the Tide team deploys. A new realm also has human-only licence/Terms and account-link steps; “self-service” below means no Tide-team deployment, not unattended setup. [canon/concepts.md:1-10; scenarios/relationship-attestation--scenario.md:86-105,139-175; canon/custom-contracts.md:1-10,71-80; templates/templates/shared/bootstrap-tidecloak.sh:65-124,434-486]

**Evidence notation.** All effort ratings, product-screen proposals and example rankings are **[INFERENCE]**, not measured build results. “Y” assumes an existing licensed realm, a compatible ORK network, and the required people completing browser enrolment. The actual local realm/network’s relationship-contract support is **[UNVERIFIED]** in this read-only review; the scenario says support is assumed on networks updated since 2026-10-16. [scenarios/relationship-attestation--scenario.md:21-34; misc/tide_gaps.md:100]

## 3. IGA approvals: mechanics and app boundary

- **Approver role/auth:** admin REST calls use a bearer token with `manage-realm`; `tide-realm-admin` is a **client role** on `realm-management`. In FirstAdmin, threshold is 1 and any `manage-realm` admin signs server-side with VRK. In Tide MultiAdmin, an enclave signature is required and approvals are credited to the authenticated HTTP caller. [canon/iga-change-requests-api.md:26-35,92-113,194-201; scenarios/iga-admin-governance--roles.md:9-34]
- **Quorum:** the fallback/projected formula is `max(1, floor(0.7 × active tide-realm-admins))`; the **live gate is the threshold in the signed `tide-realm-admin` policy**, not necessarily that formula. For example, N=2 yields fallback threshold 1; do not promise two votes just because two admins exist. Inspect the request’s `threshold`. [canon/iga-change-requests-api.md:194-201]
- **What changes:** 18 specific admin API actions on a non-master, IGA-enabled realm create CRs; not every mutation. Governed categories include user create, user role grant/revoke, group membership, certain role/composite changes, some client/scope changes, licence rotation and policy changes. Master realm and IGA-disabled realms are exempt. Vendor record says role creation is auto-approved/audit-only, but current dev observations saw `CREATE_ROLE` and `SET_USER_ATTRIBUTE` return accepted/pending and unapplied; inspect CRs and read back state. [canon/concepts.md:126-132,168-172; misc/tide_gaps.md:71]
- **Current API (base `/admin/realms/{realm}`):** [canon/iga-change-requests-api.md:26-52,56-90,127-142]

| Operation | Request / response meaning |
|---|---|
| Governed admin write | Original write returns **202 Accepted** + `Location` to CR; not proof it applied. |
| List/get | `GET /iga/change-requests?status=PENDING` returns array with top-level `id`; `GET /iga/change-requests/{id}` returns one CR. |
| Unified approval (use this for app UI) | `POST /iga/change-requests/{id}/approve`, first body `{}`. Returns `mode:"recorded"` or `mode:"needs-approval"` plus base64 `requestModel`. Decode/present to enclave; then POST same endpoint with `{"requestModel":"<base64 signed request>"}`. Approval auto-commits at quorum. Read `mode`, `committed`, `authCount`, `threshold`, `readyToCommit`, `status`. |
| Back-compat authorize/commit | `POST /{id}/authorize` body `{}` optional records approval but does **not** commit and refuses Tide MultiAdmin; `POST /{id}/commit` applies once ready. Prefer `/approve` in a current UI. |
| Deny / older enclave route | `POST /{id}/deny` optional `{"reason":"..."}`; `GET/POST /{id}/approval-model` is older back-compat, not the current console lane. |
| Lifecycle | `PENDING`, `APPROVED`, `DENIED`, `CANCELLED`; `APPROVED` means committed/applied. List CR uses `authorizationCount` and `authorizers[]`; do not assume response’s `authCount` exists in the list. |

**Can an app show pending requests and an Approve action? Yes.** The governance scenario explicitly has an app list pending CRs and approve; implement `GET` + `POST .../approve` and enclave handling. The **human** must complete the enclave signature in a browser. A custom app can do this; using Tide’s built-in console is not mandatory if the app implements the flow. Send each approval directly from that admin’s browser with their own DPoP-bound token—not through a server proxy, which credits all votes to one service account. [scenarios/iga-admin-governance--scenario.md:86-97; canon/iga-change-requests-api.md:60-90,92-123]

**Token propagation:** after a role change is committed, refresh/re-auth is needed; new claims can take up to **120 seconds** to appear in the JWT/doken. [canon/concepts.md:163-170; feature-mapping.md:343-348]

## 4. RelationshipAttestation: grant, use and revoke

**Grant shape:** one signed `RelationshipAttestation:1` policy per **(subject, record)**. Params are `subjectType` = `User|Group|Role`, `subjectId`, optional `clientId` for a client role, `assignmentId` = record id, `roles` = JSON-array string (`_tide_decryptor`, `_tide_encryptor`, or both). Every encrypted item has exactly one tag: that record id. `User` uses grantee’s `tideuserkey`; `Group` uses exact full path in token claim `groups`; `Role` uses role name. [scenarios/relationship-attestation--scenario.md:41-84,86-105; templates/templates/relationship-attestation/relationship.ts:90-130]

**Who grants:** a `tide-realm-admin` signs the policy in their authenticated browser; the enclave approval is the grant. The helper builds `Models.Policy`, calls `PolicySignRequest.New`, `createTideRequest`, `requestTideOperatorApproval`, attaches the signed admin policy and calls `executeSignRequest`. The app may provide this admin screen and store the returned policy bytes; the data owner is not the signer unless that person is also the realm admin. [scenarios/relationship-attestation--roles.md:5-14,38-56; templates/templates/relationship-attestation/relationship.ts:133-167]

**Can a data owner grant one record to one named user/group/role? No.** A realm admin can grant all three subject types; a data owner cannot. For `User`, the grantee must have signed in once; for a group/role, membership itself controls access and is IGA-governed. [scenarios/relationship-attestation--scenario.md:86-105,139-140; scenarios/relationship-attestation--roles.md:46-56; scenarios/relationship-attestation--bootstrap.md:97-104]

**Revoke / limits:** deleting the stored policy only stops the app serving that copy; a recipient who kept signed policy bytes can still use it. Remove a member from a `Group` or remove a `Role` to block future use after the credential next refreshes; that revokes access across every record covered by that group/role. Removing `_tide_decryptor` cuts all records for that user. For one user+one record, there is no instant certain revoke: use short expiry and re-grant, or a group dedicated to that record and remove membership. The contract does not stop plaintext being re-shared after decrypt; it does not protect app API routes. [scenarios/relationship-attestation--scenario.md:161-188]

**What `attestation` can do instead:** an owner-mode signed statement can say the owner shared a resource, but that scenario requires a custom contract and a realm-admin-signed rule; the server rebuilds and verifies the statement. It does not grant ORK decryption, does not make owner control of an encryption policy, and is not a third-party portable certificate. General `attestation` is therefore not a self-service substitute for owner-managed access. [scenarios/attestation--scenario.md:52-90,115-160,180-197; canon/custom-contracts.md:1143-1179]

## 6. Three original self-service ideas

All three use the existing built-in per-record contract, **with a realm admin—not the person who owns the data—granting the recipient group/role**. Each is [INFERENCE]; the “new possibility” is the product claim to make visible. [scenarios/relationship-attestation--scenario.md:36-84,86-105]

1. **Campus lab incident handoff:** a student’s incident note and photos are encrypted for the assigned lab-safety response group, so a ticket-service breach does not expose the report before the correct responders open it.
2. **Repair-diagnostics envelope:** a phone owner attaches private crash logs to a repair ticket, and only the assigned technician group can decrypt them, reducing exposure of tokens, personal paths or account data to the service operator.
3. **Scholarship appeal evidence locker:** an applicant’s sensitive evidence is encrypted for the assigned review committee, so database operators can route the case without being able to read its contents.

|---:|---|---|---|
| 1 | **Human licence and enrolment gates** — AP-90 / AP-87. | Real licence email and Terms acceptance must come from a person; admin invite link must be opened in a browser. Do not plan an unattended realm bootstrap. | [templates/templates/shared/bootstrap-tidecloak.sh:65-124,434-486; scenarios/relationship-attestation--bootstrap.md:1-19,89-104] |
| 2 | **No self-service owner grant/revoke.** | Care Passport, applicant sharing and creator-chosen recipients are not credible if framed as data-owner control; built-in grant is realm-admin-only. | [scenarios/relationship-attestation--scenario.md:86-105,139-174; scenarios/relationship-attestation--roles.md:46-56] |
| 3 | **Custom contract deployment is withheld from students.** | Policy signing, generic attestations, custom time/amount/quorum rules and provenance cannot be demonstrated live without Tide-team deployment. | [canon/custom-contracts.md:1-10,49-80,590-595; scenarios/attested-provenance-registry--bootstrap.md:165-213] |
| 4 | **No headless auth/signing — GAP-064 / GAP-063, `STILL_UNRESOLVED`.** | No device-code/service-account/headless PRISM; ORK `createTideRequest`→`executeSignRequest` is JS SDK/browser-only. Do not design a server/agent as signer. | [misc/tide_gaps.md:93-94; canon/agent-authority.md:14-29; scenarios/git-pr-signing-service--scenario.md:93-100] |
| 5 | **IGA is not “all mutations”; API/status edge cases — GAP-065 `RESOLVED_BY_VENDOR`, GAP-041 `RESOLVED_BY_VENDOR` but observed divergence.** | A 2xx can mean captured, not applied; legacy `/tide-admin/change-set` is gone. Current dev observations contradict vendor’s ACTIVE-vs-DRAFT claim for role creation/attributes: list pending requests and read back state. Direct browser approvals also must not be proxied (AP-89). | [canon/iga-change-requests-api.md:1-20,38-68,92-123; canon/concepts.md:126-132,168-172; misc/tide_gaps.md:71,95] |
| 6 | **Role-claim propagation can take 120s.** | A just-approved role may not be in the token/doken; design a refresh/re-login state rather than showing a false denial or success. | [canon/concepts.md:163-170; feature-mapping.md:288-299,343-348] |
| 7 | **DPoP relay copy can break silently — GAP-068 `STILL_UNRESOLVED`.** | A stale `tide_dpop_auth.html` can return 200 yet break popup fallback; use the pack checker and known-good asset, not a random copied file. | [misc/tide_gaps.md:98; templates/scripts/check-dpop-asset.sh:6-25,29-66; templates/templates/shared/tide-doctor.sh:10-24,151-219] |
| 8 | **Network and independent-verifier assumptions — GAP-078 `RESOLVED_BY_RUNTIME_TEST`; GAP-071 `STILL_UNRESOLVED`.** | Relationship contract is verified on ORK `main`, but this realm’s network was not probed; third-party verifiable claims also lack a public VVK endpoint (OIDC JWKS is the wrong RSA key). | [misc/tide_gaps.md:99-100; scenarios/relationship-attestation--scenario.md:21-34; canon/verifiable-claims.md:76-104] |

**Build choice:** if the team wants a live Tide-enforced demo in the remaining window, choose a single record protected by self-encryption or `RelationshipAttestation`, and make the realm-admin grant visible. If the idea’s “new possibility” requires the patient/applicant/creator to grant access themselves, or needs a custom signer/contract, say that it is not self-service instead of staging a mock as Tide enforcement.
